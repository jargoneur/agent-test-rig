# Analysis Protocol for Scaffold Boundary Conditions**Status:** binding before core launch**Date:** 2026-08-07## Research questionThe core experiment asks where each context-management scaffold helps, stopshelping, or harms performance relative to the no-scaffold condition as tasktype and complexity, model family, model size, and dense versusmixture-of-experts architecture change. Cost is not a research factor.The experimental unit is one paired block: one model, task, and repeatcontaining all five conditions on the same host with the same model artifact,deployment profile, and derived seed. All primary scaffold contrasts are pairedwithin this block.## OutcomesContextBench final-context, trajectory, and edit-localization metrics areprocess outcomes. They measure context retrieval, use, precision, coverage,redundancy, and whether edits occur in annotated regions. They do not establishthat an issue was functionally solved.The experiment therefore reports separate outcome families:1. ContextBench retrieval and trajectory metrics at their native   file/symbol/span/line granularities.2. Patch presence and available edit-localization metrics.3. Terminal outcome kind, including no patch, context rejection, OOM, invalid   response, scaffold failure, and other recorded model/scaffold outcomes.4. Infrastructure failures and retries, reported separately and never treated   as model outcomes.No composite success score will hide tradeoffs among recall, precision,efficiency, patch production, and terminal failure. No-patch outputs are scoredas zero predicted edits; they must never inherit the gold patch. Evaluatorerrors such as no context extracted remain explicit observed results.## Primary contrastsFor every metric and terminal-outcome indicator, compute the paired difference:    scaffold condition minus no_scaffoldwithin each model, task, and repeat. Report the distribution, median and meanpaired effect, uncertainty interval, and the proportion of blocks with positive,zero, and negative effects. Repeats remain paired and are not presented asindependent tasks.Primary results are stratified by:- model family;- model size within family;- dense versus mixture-of-experts architecture;- continuous frozen task-complexity score and its easy/intermediate/hard bins;- source-declared task type;- frozen solution-scope labels.Qwen and Gemma are analyzed separately before any cross-family description.Dense and mixture-of-experts checkpoints are not placed on one unqualified sizecurve. For MoE models, total and active parameter counts are reportedseparately.## Boundary definitionsA scaffold is useful in a region when its paired effect over no_scaffold ispositive for the outcome being discussed. Diminishing effect means the pairedadvantage approaches zero as model size or task complexity changes. Negativeeffect means the paired effect is below zero. These labels are alwaysmetric-specific.Boundary estimates use within-family interaction models and segmented ormonotone size/complexity trends only when supported by the observed ladder.Report the interval of plausible crossover values rather than a single exactthreshold. A boundary is descriptive when sample support is sparse or aninterval spans the observed ladder.The selected corpus contains 112 maintenance bug-fix, 36 feature, and 2refactor tasks. Refactor results are a census of the available source categorybut are descriptive, not a stable task-type boundary estimate. Thedocumentation/configuration and cross-module labels describe solution scope;they must not be relabeled as source-declared task types.## Failure and missingness rulesEvery completed terminal model or scaffold result is usable data. It remains inthe denominator and contributes to its terminal-outcome indicator even whenContextBench cannot extract a trajectory metric. Metric values are not imputedfrom other conditions, the gold patch, or another repeat.Only infrastructure failures may retry, with at most two retry-consumingfailures. Manual stops and resource yields do not consume that budget. Aninterrupted block is rerun in full from fresh state; partial condition resultsare never reused.A condition summary is incomplete unless it contains all expected task recordsor explicitly lists the missing infrastructure records. Failure rates,evaluator-error rates, and retry counts accompany every metric table.## Inference and multiplicityUncertainty must respect pairing and task clustering. The primary presentationuses paired task-level resampling within the declared strata. Model-laddermodels include task effects and scaffold interactions; they do not treat24,750 runs as independent observations.All five conditions, primary metrics, strata, transformations, and exclusionsare declared before launch. Report effect sizes and intervals. If formalhypothesis tests are added, adjust within each declared outcome family and keepexploratory analyses labeled separately.## Reproducible outputsThe raw run JSON is immutable. Evaluation produces, for everymodel/scaffold/repeat condition:- ContextBench predictions JSONL;- ContextBench metrics JSONL;- terminal outcomes JSONL;- counts of terminal kinds and evaluator errors;- a condition index with exact input and output paths.Analysis inputs are content-addressed. Deterministic scripts, frozen labels, andrecorded provenance replace manual result review or subjective adjudication.Any later benchmark or task expansion is a separate append-only experiment andmust not silently change the core estimand.
